# Deploy

本目录用于存放第一周基础版部署文件，当前采用的思路是：

- 前端：通过 Docker 构建静态资源，并在容器内由 Nginx 通过 `80` 端口提供页面
- 后端：通过 Docker 构建 Spring Boot 可执行 jar，并在容器内通过 `8080` 端口提供服务
- 网关：由独立的 `nginx` 服务对外暴露 `80` 端口，并把 `/`、`/api/`、`/health` 分发到前后端
- 数据库：优先作为服务器上的独立 MySQL 服务部署，不和当前 Compose 一起编排

## 当前文件说明

- `docker-compose.yml`：编排 `frontend`、`backend`、`nginx` 三个服务
- `nginx.conf`：定义前端静态页与后端接口的反向代理规则
- `.env.example`：服务器部署时需要补齐的环境变量模板

## 数据库处理方式

当前阶段推荐将 MySQL 独立部署在服务器上，再由后端容器通过环境变量连接数据库。

优点：

- 数据不跟随前后端容器一起频繁重建
- 更符合后续服务器长期运行的方式
- 应用故障与数据库故障可以分开排查

因此当前 `docker-compose.yml` 中不直接编排 `mysql` 服务，而是要求服务器先准备好：

- MySQL 8.x
- 业务数据库
- 业务账号和密码

后端连接数据库所需变量通过 `.env` 注入。

## 环境变量使用方式

服务器部署时，建议在本目录下复制一份：

```bash
cp .env.example .env
```

然后根据实际服务器情况修改 `.env`，至少包括：

- Spring Boot 运行环境
- 数据库连接地址
- 数据库账号密码

## SQL 执行约定

数据库 SQL 文件统一维护在上级目录的 `sql/` 中，由数据库同学在本地编写并提交仓库，再由服务器同学在服务器上执行。

当前阶段先确定目录和执行约定，不预生成具体 SQL 文件。后续可按数据库设计结果补充建库、建表和初始化数据脚本。

## 第一周最小部署目标

- 前端静态页可访问
- 后端 `/health` 可访问
- 后端可通过环境变量连接服务器上的 MySQL
- 部署日志可以通过 GitHub Actions 和服务器终端定位问题
