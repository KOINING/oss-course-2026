# 第二周至第八周总体任务规划

本文件用于指导项目从**第二周开始**到**第八周结束**的整体推进节奏。  
本版规划的核心调整是：

- **第 2 周到第 6 周完成全部核心开发任务**
- **第 7 周开始不再新增核心功能，只做联调、测试、部署、文档和答辩准备**

也就是说，平台的主体功能必须在**第七周开始之前**基本开发完成。

## 二、当前项目真实起点

截至现在，项目已经具备以下基础：

### 1. 已实现部分

- 前端基础工程已完成
- 登录页、后台 Layout、首页、404 页面已完成
- token 存储、刷新后用户信息恢复已完成

### 2. 尚未完成部分

- 模块 A 只有少量真实功能，基础数据、毕业要求、指标点、宏观矩阵尚未整体闭环
- 模块 B 课程目标、内部权重、考核点仍未落地
- 模块 C 成绩模板生成、Excel 导入、课程级计算、专业级计算均未完成

### 3. 规划压缩后的基本判断

如果要保证**第 7 周之前完成开发任务**，就必须：

- 第 2 周到第 4 周完成所有配置类模块
- 第 5 周到第 6 周完成所有计算与报表相关开发

## 四、总体推进原则

### 1. 开发必须前置

第 7 周前必须完成全部核心功能开发，不能把计算、报表、导出拖到最后一周。

### 2. 依赖顺序必须严格

后续开发顺序固定为：

`基础字典 -> 毕业要求/指标点 -> 宏观支撑矩阵 -> 课程目标/内部权重/考核点 -> 教学班/学生/成绩导入 -> 课程级计算 -> 专业级计算 -> 报表导出`

### 3. 每周至少形成一个真实业务闭环

每周新增内容至少要满足：

- 页面可访问
- 接口可调用
- 数据可落库
- 角色可联调

### 4. 第 7 周开始禁止再开大坑

第 7 周开始只允许：

- 修 Bug
- 调整交互
- 补测试
- 补文档
- 稳定部署

不再开启新的核心业务模块。

## 五、按当前团队配置适配的并行思路

结合 [team.md](/C:/Users/32484/Desktop/开源软件通识/oss-course-2026/docs/team.md) 和当前最新安排，后续总体推进不再保留“独立服务器部署角色”，数据库工作也不再由两位同学平分，而是调整为以下 5 条实际工作线：

- 前端线
- 后端线
- 数据库线
- 测试与联调线
- 统筹与部署线

这意味着每周任务设计都要保证：

- 前端有明确页面和交互工作
- 后端有明确接口和规则工作
- 数据库有明确表结构、样例数据、约束工作，并由一位同学持续收口
- 测试与联调有人专门承担联调验证、问题复测、操作路径梳理
- 组长除统筹外，还需要承担环境、运行、部署说明和最终演示链路收口

### 当前人员调整原则

- **部署工作**：从第二周开始，不再设置独立服务器/部署角色，由组长统一负责部署相关工作与运行说明收口
- **数据库工作**：从第二周开始，数据库相关工作统一由**支佳璇**负责
- **其余空出的人员**：优先补到后端支援、测试联调、文档收口等对后续总进度影响更大的环节

- 第 4 周：课程目标、内部权重、考核点

### 2. 技术稳定主线

- 每周至少 1 次中期联调
- 每周收口接口字段和返回结构
- 每周清理不应提交的构建产物

- 每周更新接口说明
- 每周更新联调问题清单
- 每周形成周验收结论
- 每周同步更新环境与运行说明
- 第 8 周完成最终文档定稿

## 八、必须提前规避的风险

### 1. 把开发拖到第 7 周以后

这是当前最需要避免的风险。  
如果第 7 周还在开发核心功能，最后两周就会同时承受开发、测试、部署、答辩四重压力。

### 2. 提前分散精力做非核心增强

当前不应优先投入过多时间在：

- Redis 接入
- 非必要性能优化
- 复杂 UI 美化
- 可替代的高级组件重构

主链未通前，这些内容都应让位于业务落地。

### 3. 只做页面不做规则

本项目的难点不在页面数量，而在：

- 权重校验
- 计算链路
- 锁定状态
- 可追溯结果

如果只把界面搭起来，后面返工会非常大。

## 九、一句话总规划

从第二周到第八周，项目的正确节奏应该是：

**前 5 周半集中完成全部核心开发，第 6 周收尾开发与全链路打通，第 7 周起只做联调、测试、部署、文档和答辩准备。**

只要严格守住这个节奏，第 7 周之前完成开发任务是可实现的，后两周也才有足够空间把项目真正打磨成可验收、可展示、可答辩的完整平台。
